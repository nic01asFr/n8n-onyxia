n8n pour Onyxia

Ton instance n8n sur SSPCloud, prête en deux minutes : éditeur de workflows, webhooks publics, et un serveur MCP pour que ton assistant IA construise les workflows avec toi.

Installer Code source

n8n relie des API, des bases et des fichiers par des workflows visuels. Ce chart le lance dans ton espace SSPCloud comme n'importe quel service Onyxia : URL publique, mot de passe affiché dans « Mes services », données sur un volume persistant. Le serveur MCP livré avec lui donne à Claude, Cursor ou tout client MCP de quoi lire, créer et déboguer tes workflows.

Promesse Ce que ça change

  • Un service Onyxia comme les autres Formulaire, bouton « Ouvrir », mot de passe à copier, mise en veille : le chart suit les conventions des catalogues officiels InseeFrLab.
  • Rien d'ouvert par défaut Le compte owner existe dès le démarrage, le serveur MCP exige un jeton Bearer, et la clé API qu'il utilise ne touche ni aux utilisateurs ni aux réglages de sécurité.
  • Tes données restent chez toi Workflows, credentials chiffrées et base SQLite vivent sur un volume de ton namespace. PostgreSQL Onyxia en option.

API REST, bases de données, S3, messageries, LLM : chaque nœud se configure dans l'éditeur, les credentials sont chiffrées.

Parcours Le parcours

  1. 1
    Tu lances le service

    Depuis le catalogue Onyxia, ou en une commande depuis un terminal Jupyter. Onyxia renseigne l'adresse, ton email et un mot de passe à usage unique.

  2. 2
    Le pod se prépare seul

    Un conteneur annexe crée ton compte owner avant que quiconque n'atteigne l'URL, puis une clé API aux droits limités pour le serveur MCP. Aucun droit Kubernetes n'est demandé.

  3. 3
    Tu ouvres l'éditeur

    Le bouton « Ouvrir » d'Onyxia mène à n8n ; identifiant et mot de passe sont dans les notes du service, avec le bouton de copie.

  4. 4
    Tu branches ton assistant

    Les notes donnent l'adresse MCP, le jeton et la commande « claude mcp add » prête à coller. Tu décris un workflow, l'assistant le construit dans ton instance.

Installer Trois façons de lancer n8n

Terminal Jupyter

Lance un service Jupyter avec le rôle Kubernetes Edit, puis :

curl -sL https://nic01asfr.github.io/n8n-onyxia/install.sh | bash

Hôtes, mot de passe et enregistrement dans « Mes services » sont faits pour toi.

Catalogue Onyxia

Une fois ce dépôt référencé comme catalogue par les administrateurs de ta plateforme, n8n se lance depuis le formulaire, comme les services officiels.

https://nic01asfr.github.io/n8n-onyxia/index.yaml

Adresse du dépôt Helm à déclarer côté Onyxia.

Helm

Pour régler chaque valeur toi-même :

helm repo add n8n-onyxia https://nic01asfr.github.io/n8n-onyxia
helm install n8n n8n-onyxia/n8n --version 1.0.1 \
  --set ingress.hostname=user-IDEP-n8n.user.lab.sspcloud.fr \
  --set mcp.hostname=user-IDEP-n8n-mcp.user.lab.sspcloud.fr \
  --set ingress.ingressClassName=onyxia \
  --set security.email=toi@exemple.fr \
  --set security.password=N8n-motdepasse

Assistant Brancher Claude sur ton n8n

Les notes du service donnent l'adresse et le jeton exacts. Avec Claude Code :

claude mcp add n8n --transport http https://user-IDEP-n8n-mcp.user.lab.sspcloud.fr/mcp \
  --header "Authorization: Bearer <jeton affiché dans les notes>"

Puis demande par exemple : « Crée un workflow qui récupère chaque matin le flux RSS de l'Insee et me l'envoie par mail. »

Usages Quand ça compte

Automatiser une chaîne de traitement

Récupérer un fichier chaque nuit, le déposer sur ton S3 SSPCloud, prévenir l'équipe.

Le planificateur de n8n tourne dans ton espace, près de tes données.

Recevoir des webhooks

GitHub, un formulaire, un outil métier : n8n expose une URL publique en HTTPS pour chacun.

Prototyper avec un assistant

Tu décris le besoin en langage naturel ; l'assistant cherche les bons nœuds, écrit le workflow et lit les exécutions en échec.

Le serveur MCP connaît le catalogue complet des nœuds n8n.

Pourquoi un chart dédié

Lancer l'image n8n ne suffit pas sur SSPCloud : l'écran de création du compte admin reste ouvert au premier visiteur, et un mot de passe rangé dans un Secret Kubernetes est introuvable depuis l'interface. Ce chart règle les deux sans droit supplémentaire.

Migration Depuis les charts 0.x

Les charts 0.x installaient n8n 1.x et un chart n8n-mcp séparé. Le passage à n8n 2.x migre la base : le script d'installation refuse donc de mettre à jour une release 0.x sans toi.

  1. 1
    Sauvegarde

    Exporte le volume et la clé de chiffrement.

  2. 2
    Mise à jour en conservant les données

    Les charts 0.x rangeaient les données dans « .n8n/.n8n » : garde ce chemin et la clé existante.

  3. 3
    Nettoyage

    Une fois n8n vérifié, supprime l'ancienne release n8n-mcp.

kubectl exec deploy/n8n -- tar czf - -C /home/node/.n8n . > n8n-backup.tar.gz
kubectl get secret n8n -o jsonpath='{.data.encryptionKey}' | base64 -d > n8n-encryption-key.txt

helm upgrade n8n n8n-onyxia/n8n \
  --set n8n.userFolder=/home/node/.n8n \
  --set n8n.encryptionKey="$(cat n8n-encryption-key.txt)" \
  --set ingress.hostname=user-IDEP-n8n.user.lab.sspcloud.fr \
  --set mcp.hostname=user-IDEP-n8n-mcp.user.lab.sspcloud.fr \
  --set ingress.ingressClassName=onyxia \
  --set security.email=toi@exemple.fr \
  --set persistence.keepOnUninstall=true

helm uninstall n8n-mcp
